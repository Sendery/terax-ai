# Terminal Lab: one bounded window-frame transport experiment

**Deferred by the explicit [user priority update](2026-11-14-terminal-migration-priority.md). No further transport implementation or measurement is planned now. The text below preserves the earlier experiment registration.**

Registered before implementation and graphical measurement, after the negative
credit-batch confirmation in `143c139`. This stays in Phase 1. The exit answer
remains no until new valid measurements establish otherwise; phases 2 to 5 and
all normal-pane parity requirements remain gated.

## Question and architectural boundary

Does reducing frame deliveries per window improve the slowest pane's cadence?
Tauri 2.11.5's installed `src/ipc/channel.rs` routes raw bodies of at least
1024 bytes through another fetch command. The measured frames usually exceed
that threshold. The current candidate reduces credit invocations about eleven
times but still delivers every pane's frame separately. This is source-based
motivation, not proof of delivery, GPU or presentation causality.

Compare the current credit-batched candidate with that same candidate plus
window-frame delivery. Keep native Terminal ownership, generated bytes,
snapshot/frame V1, Pump and its 4 ms minimum, per-session byte queues, credit
acceptance, final frames, shared renderer and post-draw acknowledgements.
No changes to the production xterm path or ordinary engine opens. Normal
modes allocate no window transport or additional task/timer/thread.

The WASM proof already establishes limited native-core/codec link feasibility.
It does not evaluate a Worker or raw-byte transport. Moving parser ownership
would send roughly 12 GiB per payload through native-to-webview transport,
versus about 280 MiB of SGR frames in the current comparison. That tradeoff
requires an integrated experiment, not another codec microproof. This single
native window-delivery experiment will inform that architecture decision.

## Candidate contract

Use one autorun-only sandbox transport for the terminal-lab window. A lease
identifies the active run; twelve reserved routes are bound once to benchmark
sessions, never real PTYs. Validate the calling window and autorun path before
opening, looking up or closing a lease. Reject stale leases and duplicate
routes. Register the JS receiver and reserve a route before starting its
producer, including the frame that may arrive before open returns an id.
Closing prevents new submissions, queued tasks and mutation by residual JS
arrivals. A Channel send already entered cannot be physically recalled.

Enqueue an immutable V1 frame with its route and native monotonic time. A
single native main-loop task drains whatever is currently available. Never
wait for twelve frames, another display tick, a timer or a chosen batching
interval. Frames queued while sending schedule exactly one further task.
Keep every frame in per-route order, including initial and final frames;
never replace a sequence with a newer one. No task or polling remains at idle.

The synchronous FrameSink waits for its queued Channel send result so a
failed actual send still returns false and invalidates the existing engine.
Waiting is bounded by five seconds. Closing, queue overflow, scheduling or
send failure wakes/rejects all queued and in-flight waiters, invalidates the
transport and blocks further submission. No success is inferred from enqueue.
Only engine producers may wait for that receipt. No main-loop command waits
for a sink, join or operation depending on the delivery task. The main loop
never holds a transport mutex while calling callbacks, Channel.send or its
scheduler. Timeout, close and send completion resolve each receipt once;
a late success cannot clear a failure or restore transport completeness.

Bounds: twelve routes, 24 pending frames across queued and in-flight work,
256 KiB per V1 frame, and an 8 MiB owner-memory reservation covering original
pending frames plus the envelope construction copy and its headers. Reserve
for that peak before accepting another frame or copying the envelope; a frame
is still pending while its receipt is in flight. This is not a whole-process
or Tauri/WebKit allocation bound. Exceeding a bound
fails the experiment explicitly. No bytes or frames are silently discarded.
The extra envelope has magic `TXW1`, a u16 frame count and zero reserved u16,
then repeated u32 route, u32 byte length and unchanged aligned V1 frame bytes.
Validate the whole envelope before dispatching any member in JavaScript.
Reject truncation, extra bytes, unknown routes, bad headers or counts/lengths,
including the complete inner V1 frame validation before any session mutation.
Decode aligned inner frames by offset without copying; pass their validated
views to EngineSession rather than decoding twice. A profiled candidate
reports per-frame validation CPU time, application CPU time and the separate
wait between validation and application of the whole envelope. Both variants
from the same source use the same named profile fields, zero added wait on
the direct path. Do not mislabel the whole-envelope validation wait as apply
or decode CPU time.

Native statistics keep enqueued/delivered/rejected/failed/pending counts and
bytes, deliveries, sizes, high-water marks, explicit first failure and native
enqueue-to-dispatch delay aggregates. JS retains per-session frame/credit
accounting and records actual envelope arrivals/bytes/sizes. Compare totals
and barriers. No cross-clock subtraction. Existing sendMicros now includes
synchronous waiting for the window task in the candidate; it cannot be read
as only Channel.send time or compared as delivery latency with the control.

## Fixed workload, order and decision

One reviewed optimized binary and verified prebuilt core for both variants.
Record source, runner, binary and core hashes and confirm unlocked GUI and
power assertions. Never overlap native measurements with builds/tests.
Use the unchanged ASCII/SGR/TUI generators, twelve 100x30 panes, 1024 MiB per
session, full native-font backbuffer, 180 s case timeout, 250 ms warmup and
minimum 5 s common interval. Keep the report size limit and final barrier.

Run the instrumented credit-batched control twice, then instrumented
window-frame candidate twice, through separate runner calls (A,A,B,B).
Preserve every result, including short ASCII windows and explicit errors.
Report each payload/repetition, minimum individual-pane FPS, common interval,
frame/byte throughput, stage distributions, native accepted credits,
credit invocations, delivery reduction, batch sizes and added queue delay.
If it helps, confirm the window candidate twice without optional stage tuples.
Collection success is not the 60 FPS result.

This is one experiment, not a parameter sweep. Do not tune a wait, bounds,
credit size, the 4 ms Pump cadence, payload, geometry or the acceptance rule.
If it reaches 60 FPS in every pane for the fixed workload twice, document the
remaining Phase 1 comparisons and parity work before advancing. If it remains
negative, close native batching as insufficient and decide on an integrated
bounded-byte-transport Worker comparison. A lower delivery count alone does
not pass. Significant added task wait must be reported as a tradeoff, not
attributed solely to reduced Channel traffic.

## Verification before measurement

Observe failing regressions before implementing envelope encoding/decoding,
queue ordering and joint bounds, schedule/send/timeout failure, callback
reentry, close and late work. Exercise frontend route registration and cleanup,
open races, full validation before mutation, default-path isolation, strict
sandbox/autorun authority and runner completeness. Preserve final-frame and
fatal pipeline tests. Run the full existing gate floor and independent Astra
review before commit/build. Graphical measurement must then prove the actual
WKWebView path; unit success alone does not establish integration.


Pre-implementation independent Astra review found no conceptual blocker with
the route-before-producer, producer-only wait, single receipt resolution,
residual-send, peak reservation and whole-envelope validation conditions
above. No native measurement has run for this transport.
